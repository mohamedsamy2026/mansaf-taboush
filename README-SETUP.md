# مشروع منسف طبوش — دليل الإعداد والربط

المشروع هو نسخة React/Vite من تصميم المطعم الأصلي، مع لوحة إدارة متصلة بـ Supabase. تم الحفاظ على مكونات الموقع وتنسيقاتها الأصلية، وإضافة لوحة الإدارة بمظهر خمري/ذهبي/كريمي. **طلبات العملاء تُرسل إلى واتساب فقط ولا تُخزَّن في قاعدة البيانات**.

## 1. قبل البداية

- يتطلب Node.js حديثًا ووجود مشروع Supabase مفعل.
- **لا تضع كلمة سر قاعدة البيانات ولا `service_role` ولا `secret key` في الموقع أو ملفات .env التي تبدأ VITE_.**
- يمكن استخدام أي بريد إلكتروني تملكه لإنشاء الأدمن؛ يجب أن يكون حسابًا حقيقيًا يمكن تسجيل الدخول به، دون وضع كلمة السر في كود الموقع.
- البيانات الأولية في ملف SQL **تجريبية** وليست أسعارًا مؤكدة من صاحب المطعم.

## 2. نفّذ ملفات SQL بالترتيب — مهم جدًا

1. افتح **Supabase Dashboard → SQL Editor → New query**.
2. افتح `supabase/01_schema_and_security.sql`، انسخ المحتوى كاملًا، اضغط **Run**. يجهّز 6 جداول وإعدادات الصلاحيات وStorage.
3. افتح `supabase/02_initial_data.sql`، انسخه كاملًا واضغط **Run**. يضيف وجبات وأقسام وإعدادات المطعم المبدئية. يُنفَّذ بعد الملف الأول.
4. افتح **Authentication → Users → Add user**؛ أنشئ مستخدمًا بإيميل وكلمة مرور قوية. يجب أن تكون بيانات الدخول فعّالة والإيميل مؤكدًا إذا كان التأكيد مطلوبًا. **لا تشارك كلمة السر هنا في المحادثة أو داخل GitHub.**
5. افتح `supabase/03_grant_admin_TEMPLATE.sql`. استبدل فقط `ADMIN_EMAIL_HERE` بالبريد الإلكتروني الذي أنشأته (داخل علامات الاقتباس) ثم نفّذه في SQL Editor. هذا يمنح الحساب صلاحية الأدمن من جدول مستقل؛ مستخدم Auth عادي لا يحصل على الإدارة وحده.
6. **لو أنت نفّذت الملفات الثلاثة بالفعل في مشروع Supabase الحالي:** افتح `supabase/04_reorder_categories.sql`، انسخ المحتوى إلى **SQL Editor → New Query → Run** مرة واحدة. الملف ده ضروري لحفظ ترتيب الأقسام بأسهم فوق/تحت وبشكل آمن. لا تعيد تشغيل ملف 02 الخاص بالبيانات التجريبية.
7. **اختبر الصلاحيات:** جرّب دخول `/admin` بالإيميل والباسورد. لو الحساب موجود في Auth ولكن لم تنفذ الخطوة 5، سيظهر "غير مصرح".

> عند تسليم الموقع للعميل: أنشئ حسابه الجديد في Authentication، نفّذ سطر INSERT للمنح بالإيميل الجديد، جرّب دخوله، ثم احذف صلاحيات حسابك القديم من `public.admin_users` إذا اتفقتم. لا تشارك كلمة سر حسابك الشخصي.

## 3. إعداد متغيرات الاتصال

1. من **Supabase → Project Settings → API / Connect** انسخ **Project URL** و **Publishable key أو anon key** فقط.
2. في جذر المشروع، انسخ `.env.example` إلى ملف جديد اسمه `.env`.
3. غيّر القيم:

```env
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_PUBLISHABLE_OR_ANON_KEY
```

4. ملف `.env` موجود في `.gitignore` لمنع رفعه إلى GitHub.
5. شغل الأوامر في مجلد المشروع:

```bash
npm install
npm run dev
```

6. افتح `http://localhost:5173/admin` لتسجيل دخول الأدمن، أو صفحة الموقع الرئيسية للعملاء.
7. لا تستخدم الموقع تجاريًا قبل مراجعة الأسعار والمنتجات التجريبية مع العميل.

## 4. النشر على Vercel

- ارفع كود المشروع إلى GitHub بعد التأكد أن `.env` غير مرفوع.
- في Vercel: **Framework Preset: Vite**، **Build Command: `npm run build`**، **Output Directory: `dist`**.
- أضف `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY` إلى **Environment Variables** في Vercel. إعادة النشر ضرورية بعد تحديثها.
- ملف `vercel.json` موجود لدعم فتح مسارات `/menu` و`/admin` مباشرة بعد Refresh.
- تم جعل أمر build يستدعي Vite عبر `node` مباشرة لتجنب خطأ صلاحيات تنفيذ `/node_modules/.bin/vite` على بعض بيئات الاستضافة.
- في Supabase → Authentication → URL Configuration، اجعل **Site URL** يشير إلى الدومين الفعلي؛ عند تفعيل روابط تأكيد البريد أو الاستعادة أضف Redirect URLs المناسبة أيضًا.

## 5. إدارة بيانات الموقع

لوحة الإدارة `/admin` تشمل:

- **الوجبات:** إضافة وتعديل وحذف نهائي؛ تحديد القسم؛ الصورة؛ الاسم والوصف العربي؛ الاسم والوصف الإنجليزي الاختياري؛ الأسعار؛ أحجام ديناميكية غير محدودة.
- **الأقسام:** إضافة وتعديل وحذف نهائي، وتحريك الأقسام بأسهم فوق/تحت؛ يُحفَظ الترتيب مباشرة في Supabase. **حذف قسم يمسح كل وجباته وأحجامها بسبب ON DELETE CASCADE.** تظهر رسالة تأكيد.
- **التواصل:** كود الدولة ورقم الهاتف منفصلان عن كود الدولة ورقم واتساب؛ تغيير رموز العملة ورسوم التوصيل؛ اختيار منتج زر الهيرو.
- **الشعار:** رفع شعار جديد؛ يُستخدم ديناميكيًا في الهيرو والهيدر والفوتر.
- **السوشيال:** المنصة تختار من قائمة بأيقوناتها. الروابط غير المُضافة تختفي من الموقع. يمكن إظهار أو إخفاء اسم الحساب الاجتماعي.
- **إدارة الصور تلقائيًا:** لا يوجد زر تنظيف يدوي؛ اختيار الصورة يعرض معاينة محلية، ولا يتم رفعها إلى Storage إلا عند الضغط على «حفظ».

إذا لم تدخل اسمًا/وصفًا بالإنجليزي يظهر النص العربي في النسخة الإنجليزية تلقائيًا.

## 6. الصور والحذف النهائي

- تُضغط الصور قبل رفعها باستخدام Canvas إلى **WebP**، بحد أقصى 1400px للمنتج و1000px للشعار، وحجم مُخرَج أقصى 2MB.
- يقبل الرفع JPG/PNG/WebP، ولا يقبل SVG لحماية التخزين من المحتوى النشط.
- تظهر رسالة تأكيد واحدة قبل حذف وجبة أو قسم. بعد التأكيد يتم الحذف النهائي من قاعدة البيانات (والأحجام تحذف تلقائيًا عبر CASCADE)، ثم حذف صور Storage غير المستخدمة تلقائيًا.
- عند اختيار صورة ثم الإلغاء لا تُرفع أي صورة إلى Storage، لتجنب تراكم صور غير محفوظة. عند حفظ صورة جديدة تُضغط وتُرفع، وبعد نجاح حفظ البيانات تُحذف القديمة لو لم تعد مستخدمة.
- **تنبيه:** قاعدة البيانات وStorage خدمتان مستقلتان، ولذلك لا يمكن ضمان حذف كليهما في عملية ذرية واحدة عند انقطاع الشبكة. إذا فشل حذف Storage بعد حذف السجل، تُعرض رسالة خطأ واضحة (بدون زر تنظيف)، ويُحفظ رابط الصورة محليًا لإعادة المحاولة تلقائيًا عند دخول الأدمن من نفس المتصفح في المرة القادمة. يُنصح بالتأكد من اختفاء الصورة من Storage؛ لو مُسحت بيانات المتصفح قبل إعادة المحاولة قد يحتاج المطوّر متابعة الإزالة.
- حذف سجلات Postgres/Storage نهائي من البيانات النشطة **لا يعني التحكم في النسخ الاحتياطية التي تحتفظ بها Supabase بشكل منفصل**.
- الأصول الأصلية للموقع داخل `public/images/` تُترك كما هي، ولا تتأثر بتنظيف ملفات Storage.

## 7. الحماية

- RLS مفعّل على جداول المنتجات والأقسام والأحجام والتواصل والروابط، بالإضافة إلى جدول أدوار الأدمن.
- الزائر يقرأ بيانات القائمة العامة فقط؛ لا يمكنه إدخال أو تعديل أو حذف أي من هذه الجداول.
- الإدارة تتطلب **Supabase Auth** + وجود `auth.uid()` في `public.admin_users`، ويتحقق Postgres من ذلك في سياسات RLS.
- سياسات `storage.objects` تمنع رفع/حذف الملفات لغير الأدمن وتحدّد المسارات والامتدادات المسموح بها.
- كل صور المطعم المنشورة ضمن Bucket عام؛ يُسمح للجميع بمشاهدتها ولكن ليس بتعديلها.
- لا يوجد تسجيل حساب أدمن من الموقع؛ يُدار إنشاء الحساب ومنح الدور فقط من Supabase Dashboard وSQL Editor.
- RLS أساس الحماية، لكن ينبغي أيضًا متابعة تحديث مكتبات الموقع وتفعيل MFA للأدمن إن أمكن ومراجعة السياسات بعد أي تعديلات مستقبلية.

## 8. التجربة والتحقق

1. بعد تشغيل `npm run dev`، تأكد من ظهور القائمة والصور. افتح `/admin`، ثم جرّب دخول المستخدم المصرّح له.
2. أضف قسمًا جديدًا ثم استخدم سهم أعلى/أسفل لتغيير موقعه. حدّث الصفحة وتأكد من استمرار الترتيب. أضف وجبة بالحجم الصغير والكبير، وعدّل الأسعار وتحقق من تحديث واجهة العملاء.
3. احذف حجمًا وجرب السلة، ثم احذف المنتج: يجب أن يُزال من قاعدة البيانات ويُزال من السلال المحلية عند تحديث الموقع/إعادة تحميله.
4. اختبر رقم الاتصال مختلفًا عن رقم واتساب. تأكد أن رسالة الطلب تفتح واتساب فقط **بدون تخزين طلبات**.
5. اختر صورة ثم اضغط إلغاء: تأكد أنها لم تُرفع إلى Storage. بعد ذلك احفظ JPG كبيرًا، وتأكد من ظهور WebP في Storage، واستبدل الصورة وتحقق من حذف القديمة غير المشتركة. احذف الوجبة (مع التأكيد) وتأكد من اختفاء سجلها وصورتها.
6. جرّب تسجيل الدخول بحساب Auth ليس موجودًا في `admin_users`: ينبغي منعه.
7. نفّذ `npm run build` وتأكد من نجاح البناء قبل النشر.

## 9. ملاحظات مهمة

- إن لم تنشئ `.env` يظل الموقع يعمل بالبيانات المحلية التجريبية للاطلاع فقط، لكن لوحة الأدمن لن تعمل.
- ترتيب تنفيذ ملفات SQL مهم. إذا فشل تحميل البيانات بسبب جداول غير موجودة، راجع تنفيذها أولًا.
- عند تشغيل الواجهة بمعلومات Supabase حقيقية، لا يتم الاعتماد على المنتجات التجريبية المحلية للطلبات بعد انتهاء تحميل قاعدة البيانات.
- تُكتب بيانات عمليات الإدارة على مراحل في REST API؛ في حالة انقطاع الاتصال خلال حفظ الوجبة والأحجام، راجع الوجبة وأعد الحفظ قبل متابعة باقي الخطوات.
- ملف `package-lock.json` القديم كان لا يحتوي على مكتبة Supabase الجديدة، لذلك لم يُضمّن؛ `npm install` سيُنشئ ملف قفل محدثًا. احفظه في GitHub بعد نجاح التثبيت.
- لا يمكن ضمان تشغيل Supabase فعليًا دون إعداد مشروعك وإجراء الاختبارات المذكورة أعلاه.
